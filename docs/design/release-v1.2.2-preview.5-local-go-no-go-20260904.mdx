# v1.2.2-preview.5 本地候选验收与 Go/No-Go

## 结论

**No-Go，不合并、不发布。** 候选功能、数据库、镜像、恢复和浏览器验收均通过，但仓库要求的 Web 全量格式门禁失败：`bun run format:check` 报告 386 个既有文件不符合 Prettier。候选本次直接修改的邀请抽屉文件单独格式检查通过，因此没有用一次大范围机械格式化掩盖存量问题；只要全量门禁仍为红色，本候选就不能判定为 Go。

本记录只证明本地隔离环境中的候选行为。**仅本地通过，不代表 GitHub Actions、GHCR 或生产环境通过。** 本轮没有推送、远程 PR、Actions、远程标签、GHCR 发布、部署、生产数据访问或付费渠道调用。用户提供的线上已知阻断为 GHCR `permission_denied`；它不是本轮本地验证结果，未来申请上线前仍须单独解决并取得不可变 digest 证据。

## 数据库迁移与邀请制验收

最终 PostgreSQL 实例包含迁移 1–8，`registration_invites` 有主键和 8 个业务索引，共 9 个索引。外键策略复核如下：

- `created_by → users(id)`：`ON DELETE RESTRICT`。
- `used_by → users(id)`：`ON DELETE SET NULL`。

迁移在 SQLite 和 PostgreSQL 两套引擎上验证 fresh、跨版本升级和重复执行。SQLite 测试从固定共享内存 DSN 改成每测试独立临时文件，消除了重复运行时连接生命周期互相污染；V6→Schema 8 成为显式用例。PostgreSQL 额外覆盖 100 条历史邀请数据升级及 credits 回填。

真实候选栈完成以下邀请链路：

- 50、100、自定义 275 三类邀请分别注册成功，账户初始额度精确为 50,000,000、100,000,000、275,000,000 microcredits，并存在对应账本记录。
- 注册请求注入 `role=admin` 和超大额度字段后，新用户仍为普通 `user`，额度仍精确取邀请的 100 credits。
- 无效用户名导致注册事务失败时邀请不被消费；修正输入后同一邀请可成功注册。
- 同一 75-credit 邀请并发提交两次，仅一个用户创建成功，另一请求返回“邀请已使用”。
- invalid、expired、revoked、used 四种终态页面均在真实浏览器中确认。
- 正常复制显示“已复制”；强制 Clipboard API 与 `execCommand` 同时失败时显示“复制失败，请手动选中链接复制”。

## 浏览器发现与修复

首次验证“有未保存内容时关闭邀请抽屉”发现 Drawer 与全局确认框各自的焦点陷阱交替抢焦点，最终触发 `RangeError: Maximum call stack size exceeded`。`97b3149c` 将确认框改为 Drawer 内的受控 Modal；回归时按 Tab 后焦点稳定落在“继续编辑”，控制台无递归错误。

## Host Updater 回退演练

最终镜像演练通过真实 Manager/HTTP handler、Docker Compose、PostgreSQL 和 Backend `/data`；远程 Release Compose 下载、registry pull 与 RepoDigest 查询使用确定性本地替身，未访问远端。

1. 失败前数据库值为 `before`，媒体 SHA-256 为 `6db7d803e74f1ffa7d8f5adc0bf95b3e15bf4c8373fffadf546227cc6c6742cb`，隐藏文件存在。
2. 目标迁移修改数据库和媒体后故意退出 42；自动回退进入 `rolled_back`，数据库、媒体、隐藏文件与 schema 全部恢复。
3. 同一备份再次人工回退仍为 `rolled_back`，状态和数据不变，验证幂等。
4. 人工制造 `.canvas-updater-previous` 恢复现场后再次回退，操作进入 `manual_intervention`；Backend/Web 保持停止，现场不被覆盖，验证 fail-closed。

本次最终演练耗时 96.35 秒并通过；测试自身已清理随机 Compose 项目与卷。

## 重新申请 Go 的最小条件

1. 在独立变更中建立或修复 Web Prettier 基线，使 `bun run format:check` 全量通过；随后重跑本表全部本地门禁。
2. 获得远端操作批准后推送候选，确认最终交付 HEAD 的 required GitHub Actions 全绿。
3. 解决 GHCR `permission_denied`，由最终批准提交构建并记录 version tag、SHA tag、OCI revision 与 RepoDigest 的一致关系；不得用 `latest` 代替。
4. 使用固定不可变 digest 在获批环境启动，再次核对 readiness、schema、邀请注册和备份恢复。
