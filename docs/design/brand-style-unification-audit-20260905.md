# 品牌风格统一：前台、管理后台与服务端配置分析

以当前品牌官网为视觉基准，统一登录、创作工作台和管理后台的色彩、字体、控件、导航及反馈。保留不同场景需要的信息密度：官网讲述品牌，工作台组织作品，后台处理数据。

本轮产出为分析与实施方案。基线为本地 `main` 的 `4e6703b1`，运行后端为 `a4e096e5`，两者后端代码一致。没有修改产品代码、业务配置或用户数据。

## 1. 核心结论

目前的主要问题是主题规则分散，单独改变品牌色无法覆盖全部页面。公共组件已经具备较好的复用基础，适合从主题入口和共享组件向页面逐层推进。

1. 官网的 `--ps-accent` 固定为 `#B1A4FF`，没有读取自定义品牌色。
2. 管理后台在路由主题函数和自身 `ConfigProvider` 中均使用独立主题，绕过品牌色映射。
3. 用户端同时存在基础主题、PC Brand V2、页面私有颜色和画布绘制颜色；移动端还通过 1024px 断点使用旧主题。
4. 官网和登录的白色主按钮、工作台首页的紫色主按钮、后台的中性色主按钮分别维护，主操作的视觉语义尚未统一。
5. 服务端的品牌与官网存储边界可以继续保留；需要收口的是字段用途、默认值、配置消费和保存反馈，整套业务 API 无需因视觉统一而重写。

## 4. 统一后的界面规则

### 色彩与层次

- 深色沿用官网的炭黑与偏冷灰；表面依次为页面、卡片和浮层，减少无业务意义的渐变、光晕和多层描边。
- 灰白主按钮承载“创建、生成、保存”等本页主要命令；浅紫用于品牌强调和焦点，普通选中使用低强度填充与清晰文字。
- 成功、警告、失败和运行状态保留可区分的语义色，同时显示文字或图标。不能把所有状态都改成品牌紫。
- 深色为现有默认，保留浅色模式并映射为同一套结构；不得覆盖已有用户主题选择。
- 官网和登录可以使用电影概念背景。工作台用真实作品作封面，后台使用稳定、不干扰信息阅读的表面。

### 字体、密度与形状

| 项目 | 官网/登录 | 用户工作台 | 管理后台 |
| --- | --- | --- | --- |
| 主标题 | 保留展示型层次，随屏宽缩放 | 建议 24–28px | 建议 22–24px |
| 正文 | 15–16px | 14px | 13–14px |
| 辅助文字 | 12–14px | 12px | 12px，数字等宽排列 |
| 控件高度 | 登录沿用 52px | 普通 36px、重要操作 42px | 普通 36px，表内紧凑 30px |
| 圆角 | 图片与展示模块按构图使用 | 控件 8px、内容表面 12px | 密集控件 6–8px、内容表面 12px |
| 导航 | 官网横向 80px | 统一侧栏与顶栏 | 共用尺寸体系与选中语言，保留管理菜单 |
| 过渡 | 展示动效克制 | 120–180ms 为主 | 120–180ms 为主 |

数值为建议实施基准。工具页不照搬官网的大标题和大留白；移动端通过布局和触控命中范围适配，输入文字避免过小。减少动态效果设置应覆盖全部场景。

### 导航与布局

1. Logo、字标、留白及点击行为统一；版本与更新日志放在明确的工具入口，品牌标志承担主页导航或工作区识别职责。
2. 用户端与后台共享侧栏折叠方式、顶栏高度、页标题、筛选区和内容边距规则。菜单内容与权限仍由各自业务控制。
3. 库页面采用“标题和主操作 → 搜索/筛选 → 内容 → 分页”；表格页面采用同样的信息顺序。
4. 设置采用“选择分区 → 修改字段 → 保存状态与操作”，复用已有未保存提醒。网站设置只有四个分区，适合改为紧凑分区导航；个人设置九个分区更适合保留次级导航。
5. 详情弹窗、侧栏和全页按任务体量选择。编辑短字段用弹窗，持续参照列表的详情用侧栏，多步骤生产任务用完整页面；登录保持已确认的独立整页。
6. 避免外层卡片、内层卡片、字段容器层层围边。组内使用间距和细分隔线体现层级。

### 一致的交互反馈

- 异步区域分别定义：加载、真正为空、筛选无结果、失败、权限不足、保存中、保存成功、同步待完成。
- 保存按钮只在有修改时启用；冲突保留本地草稿并提示重新读取，失败时不丢失输入。
- 本地保存与服务端同步继续区分；视觉更新不能把“已保存到本机”改成“已同步”。
- 表单错误靠近字段，页面级错误在当前内容区表达；同一失败避免同时出现重复浮条和大面积错误面板。
- 焦点、键盘操作、文字选择、自动填充、密码显示和禁用状态都纳入同一控件规范。

以上分组覆盖 22 个页面。菜单可适度收敛分组，但不因外观相近合并职责不同的设置。

优先完成网站设置和用户管理作为两个代表页，再迁移其他列表、表单和详情。用户管理的邀请、角色和积分；系统渠道的价格和模型能力；系统更新的备份与执行流程均沿用既有合同。

## 7. 服务端需要统一什么

### 配置与消费者

| 配置 | 当前消费者 | 建议处理 |
| --- | --- | --- |
| 品牌名称、Logo、favicon | 官网、登录、工作台、后台及浏览器 | 保留，补齐各处标识尺寸和备用图策略 |
| `theme.primaryColor` | 用户端品牌变量、部分 AntD 与首页；官网强调及后台未完整使用 | 接通所有展示场景；由前端派生可读的强调/选中/焦点色 |
| `auth.title`、`auth.description` | 登录页标语与说明 | 保留，后台清楚标注用途 |
| `auth.eyebrow`、`auth.liveBadge` | 当前认证页面未使用 | 核实其他消费者后清理 API/类型/默认值中的失效配置 |
| `auth.heroUrl`、`auth.heroKind`、`auth.heroPosterUrl` 及旧认证媒体资源槽 | 当前认证背景改读 `site.hero.posterUrl` | 检查资源引用后移除无用入口和合同；不要只隐藏 UI 留下可写空功能 |
| 官网/登录共用封面、联系地址、备案文字与链接 | 官网及登录 | 继续使用已更新的限定字段保存接口 |
| 完整官网草稿、发布配置与旧管理 API | 官网仍读取已发布内容，完整后台编辑器已删除 | 保留实际被读取的内容；核实集成使用再清理管理写接口，禁止误发布旧草稿 |
| 默认品牌与官网文案 | Go 与前端各有一份 | 建立单一默认定义的生成或一致性约束，保留离线默认展示 |

品牌配置与官网内容的两条存储记录承担不同职责，可以保留。用户操作入口已经统一为网站设置，无需重新加入完整官网 CMS。

### 应继续保留的合同

- JSON 响应 `{code, data, msg}`、前端统一 `request` 客户端及真实 HTTP 状态。
- 管理员授权、修订号并发检查、资源引用、审计与输入校验。
- 任务、支付/积分和同步状态的业务枚举。前端做一致的名称、图标与颜色映射，不改写服务端状态含义。
- 图片和备案链接的校验与备用展示；配置异常不能阻断登录。

### 需要补齐的体验

1. 同源标签页在品牌修订变化时更新配置；采用存储事件或广播通知，按需读取，避免高频轮询。
2. 保存成功但页面刷新失败时，提示“已保存，显示更新失败，可重试刷新”，防止用户重复写入。
3. 配置编辑页说明字段作用范围，例如“官网与登录页封面”“全站品牌强调色”，减少预期误差。
4. 对未知技术错误提供清晰摘要和诊断信息入口。保持后台可排查，普通用户能理解下一步动作。

初步判断基础风格统一不需要数据库表结构迁移。旧字段与资源的删除必须经过消费者清单和引用验证后另行实施。

## 8. 实施顺序与周日上线范围

| 批次 | 交付范围 | 完成判据 |
| --- | --- | --- |
| A：主题与公共基础 | 路由主题、品牌变量、AntD 映射、前后台外壳、按钮/输入/导航/反馈，官网和登录衔接 | 切换品牌色可作用于全部场景；深浅主题和 1023/1024 断点一致；浮层与自动填充正确 |
| B：用户高频页面 | 首页、创作、项目/素材/任务/画布库、积分、技能、插件和个人设置 | 入口、列表、卡片、筛选、详情及关键状态符合共同规范，业务操作回归通过 |
| C：后台全部页面 | 22 个页面的列表、表单、详情、图表和危险操作 | 同一套品牌视觉与后台密度；实际保存、冲突、权限、邀请和必要配置测试通过 |
| D：复杂工作台与清理 | 短剧生产、画布、导演台、时间线、分享、旧字段与样式清理 | 不改变内容几何和历史语义，媒体与性能回归通过，无残留失效配置 |

建议周日版优先完成 A，并把登录、首页、创作入口、网站设置、用户管理作为完整验收样板。A 会使其他页面同步获得基础主题；B/C/D 的局部布局与复杂交互逐批完成，不能仅凭统一底色宣称全站改造结束。

若周日仍是既定上线时间，最后阶段应留给回归和发布核对；以每批完成判据决定是否进入版本，不承诺一天内完成全部复杂页面的深度重构。每批独立提交，便于只撤回视觉变更。

### 代码组织路径

1. 在现有 `app-theme.ts`、`branding-theme.ts` 与 `pc-user-foundation.css` 的职责上收敛唯一基础定义，避免新增另一套平行主题。
2. `--ps-*`、`--admin-*`、`--creation-*` 作为页面角色别名引用共同语义变量。只有场景专有角色保留局部值。
3. 画布 DOM 与 `canvas-theme.ts` 从同一基础值派生，保持绘制层更新成本可控。
4. 公共页面框架与控件继续使用 `components/ui/pc`；后台复用基础组件，但保留管理业务组件和密度配置。
5. 迁移规则时删除同一职责的旧定义，不能持续在大 CSS 文件尾部追加覆盖；仍被测试、功能或其他场景依赖的规则先核查再移除。
6. 更新设计文档中“只覆盖 PC、不涉及 Admin”等旧范围说明，使规范与新目标一致。
