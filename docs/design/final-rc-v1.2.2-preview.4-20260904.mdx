# v1.2.2-preview.4 最终 RC 集成与上线前验收

## 最终结论

**技术候选通过，真实业务验收 No-Go。** 当前分支已达到隔离 staging 技术验收标准：前端、Backend、Canvas Agent、生产构建、候选镜像、PostgreSQL/Redis Compose、健康检查与主要真实浏览器链路均通过。测试期间发现的两个阻断问题已经在本分支修复并回归：Host Updater 未恢复 Backend `/data`，以及导演台 E2E 夹具未模拟新增公开站点接口。

真实业务验收仍不得开始，原因不是已知代码失败，而是上线手册要求的三个外部/运维门禁尚未闭环：

1. 发布负责人、监控值守、回退执行和客户沟通角色尚未实名确认。
2. 尚未在隔离的 PostgreSQL + Backend 数据卷上通过真实 Host Updater 完成一次端到端“升级失败 → 自动回退 → 业务抽样”演练；本轮只完成了停止服务后的真实数据卷归档演练和恢复脚本测试。
3. 外部 OSS/COS 等不在 Backend `/data` 内的对象仍属于人工恢复边界，尚未登记恢复来源、校验口径与责任人。

以上三项清零，并在 GitHub Actions 与 GHCR 上确认最终提交对应的不可变制品后，可重新判定 Go。健康接口返回 `200` 不能替代这些门禁。

## 最终 RC 新增修复

### P0：完整恢复 Backend 数据目录

提交 `e8992642784d182fdc5620e47b3e90c6dc76c45b` 修复了原 Host Updater 只恢复 PostgreSQL、却不恢复已备份 `backend-data.tar` 的问题，并收紧停写与失败策略：

- 目标镜像先拉取和校验，再进入停机窗口。
- 先停止 Web/Backend，确认停写后再备份 PostgreSQL 和 `/data`。
- 停止的 Backend 通过一次性 root 容器读取数据卷，不依赖已经停止的服务容器。
- 回退必须按“停服务 → 恢复旧 Compose → 恢复数据库 → 恢复 `/data` → 恢复旧标签 → 启动并验活”执行。
- 任一恢复步骤失败即保持停止并进入人工介入，不允许带着部分恢复的数据启动。
- `/data` 激活前保留当前内容；无效 tar 不触碰在线数据；检测到未清理的上次恢复现场时拒绝覆盖。

验证包含 5 个定向恢复测试全部通过，覆盖隐藏文件替换、无效归档保护、残留现场拒绝、归档标准输入流和停止服务后的 root 数据卷读取。另在隔离 Compose 的真实 Backend 卷中写入标记、停止 Web/Backend、用新命令归档并确认标记存在，随后服务恢复健康。

### 门禁可靠性：导演台公开站点夹具

提交 `1971fcfa` 为导演台 Chrome E2E 的同源 API stub 补充 `/api/public/site`。首次运行时 52 个功能断言全部通过，但新增公开站点请求产生重复 404，导致 6 个“无浏览器问题”断言失败；修复后重跑为 `58/58`，浏览器问题列表均为空。此修复只改变测试夹具，不放宽错误 allowlist。

## 发布前停止条件

以下任一成立立即 No-Go 或停止灰度：候选标签与最终提交不一致；数据库/schema/Redis 任一不健康；备份校验或恢复演练失败；邀请制边界失效；保存/加载/播放错误超过手册阈值；无法确认值守或回退负责人；外部对象恢复来源不明确。
