# 在线更新与安全回退

管理后台的“系统配置 → 系统更新”只负责管理员鉴权、展示状态和发起操作。真正的 Docker、数据库备份与服务切换由宿主机上的 `open-ai-canvas-host-updater` 执行，业务后端不挂载 Docker Socket。

```text
管理员浏览器 → Backend 管理 API → 带 Token 的 Unix Socket → Host Updater → Docker Compose
```

## 安全更新顺序

1. 从 GitHub Releases 读取包含预览版在内的最高语义版本，并与 `.env` 中固定的 `CANVAS_IMAGE_TAG` 比较。`sha-*` 这类非正式镜像标签一律视为低于正式 Release，避免把 `vsha-5509b17` 字典序比较成比 `v1.5.0` 更新。
2. 下载目标版本的 `docker-compose.deploy.yml`，执行 `docker compose config --quiet`，检查部署文件、磁盘空间和当前版本。当前标签不是 `vX.Y.Z` 或 `vX.Y.Z.N` 时，健康检查只确认服务就绪，不要求构建号和镜像标签逐字相同。
3. 拉取目标 backend/web/yingce-agent 镜像并要求存在仓库 `sha256` 摘要；下载期间旧服务继续运行，准备失败在停服前中止。
4. 停止 web/backend/yingce-agent，等待旧服务退出；PostgreSQL 和 Redis 保持运行。
5. 创建停服后的 `backup-YYYYMMDD-HHMMSS.zip.partial`，包含 PostgreSQL custom-format dump、后端数据目录 tar 和元数据；写入完成后 `fsync`、原子改名，并复核 ZIP 结构和 SHA-256。保存旧 Compose 与部署环境，并核对本地数据挂载可用于自动恢复后才进入迁移；不支持的卷会在改库前中止并恢复原容器。
6. 用目标 backend 镜像独立执行 `migrate-schema up`。整批迁移在事务和 PostgreSQL advisory lock 内完成，迁移名称与 checksum 必须匹配。
7. 将目标 backend/web/yingce-agent 的仓库 digest 写入 `CANVAS_BACKEND_IMAGE`、`CANVAS_WEB_IMAGE`、`CANVAS_YINGCE_AGENT_IMAGE`，更新 `CANVAS_IMAGE_TAG` 和 Compose 文件后启动目标版本；运行容器使用 `image@sha256:...`，不使用 `latest`。各文件使用临时文件原子替换，多个文件不是一个文件系统事务。
8. 连续检查 `/api/health/ready` 的数据库、运行时、schema 和 build version，并经过稳定窗口后才标记成功。

更新状态写入 `/var/lib/open-ai-canvas-updater/state.json`。Backend 或浏览器在切换期间断线不会终止宿主机操作，恢复后可继续读取日志。

停止服务、最终备份或旧配置保存失败且尚未开始迁移时，直接启动原容器并验证健康，不恢复旧数据库快照。原容器恢复失败会进入 `manual_intervention`。备份耗时计入停服窗口。

旧 Compose 与环境文件先暂存、检查先前回退配置，再逐个替换。环境文件替换失败时恢复先前 Compose，避免旧备份与新配置混用；连先前 Compose 也无法恢复时，清除人工回退记录并保留错误。这个错误恢复机制不等同断电时的跨文件原子事务；进程中断后的 `manual_intervention` 仍需检查现场。

数据目录归档通过原 backend 镜像的一次性容器执行 `tar`，挂载原数据卷，不启动业务入口或依赖服务，不重新拉取镜像；不再依赖已停止容器上的 `exec`。归档命令只读取数据，但没有把原 Compose 的读写挂载自动改为只读挂载。

## 自动回退

停服后的迁移、启动或健康验证失败会触发自动回退：

1. 在停服和改库前校验备份 ZIP、SHA-256、旧 Compose 和环境文件；回退版本、备份版本及旧环境中的版本必须对应；
2. 停止目标 web/backend/yingce-agent，确认停止命令成功；
3. 核对当前 backend 容器、旧 Compose 的 `/data` 挂载及本机 Docker 连接，在数据挂载内的 `.host-updater-recovery-<ID>/snapshot` 完整暂存并校验归档；在覆盖数据库前拒绝越界路径、重复路径、符号/硬链接、特殊文件、无效密钥及损坏归档；
4. 恢复更新前保存的 Compose 与 `.env`，保留三个服务的旧镜像引用；删除并重建目标业务数据库，再使用 `pg_restore --no-owner --no-privileges` 恢复 PostgreSQL；系统数据库名称会被拒绝，恢复命令使用与其他操作相同的 Compose project；
5. 将当前数据目录的顶层内容移至同一恢复目录的 `previous/`，再将快照移入活动目录；这会补回已删除文件、恢复被修改的素材及原 `.settings-key`，并把快照后新增文件移出活动目录。原文件不直接删除，旧符号链接仅移动，不访问其指向的文件；
6. 复核文件内容 SHA-256、普通权限与类型后，才启动旧服务并重新进行稳定窗口验证。归档中的 UID/GID 与普通权限在提取时恢复。启动、健康检查或完成记录写入失败时，再次停止写入服务；停服失败也会明确报告。

回退按上述顺序执行。备份或旧配置缺失、版本不对应时，在停服和改库前拒绝操作。停服、配置恢复或数据库恢复失败后，立即进入 `manual_intervention`，不继续改库或启动应用；已经停止的写入服务保留停止状态，避免旧程序接入部分恢复的数据库。管理后台仅在存在旧版本和已校验备份时开放人工回退按钮，但发起操作时仍会重新校验。

健康验证要求 `ready=true`、`started=true`、`draining=false`，数据库、运行时和 Schema 检查全部通过，Schema 当前值与预期值一致且大于零；正式 Release 还要求返回非空且匹配的构建版本。HTTP 200 和业务返回码成功不能单独作为就绪依据。

该备份覆盖旧服务停止前的写入。新版本启动后产生的业务写入不在此快照中，历史备份回退仍可能覆盖这些写入。恢复范围包括 PostgreSQL 和本地 `/data` 快照；外部 OSS/CDN 对象不在这份本地归档内，也不会被回退操作删除或恢复。启用更新器前，应在目标部署的隔离副本完成升级及失败回退演练，并核对旧 Compose、环境文件与备份记录对应关系。

本地文件自动恢复要求更新器运行在 Linux Docker 宿主机上，使用本机 Unix Socket，并能够直接访问 backend 的唯一可写 bind mount 或无额外挂载选项的标准 local 命名卷。旧 Compose 与当前容器的数据挂载必须对应；远程 Docker、带绑定/NFS 等挂载选项或其他驱动的卷、只读或嵌套挂载、更新器状态/配置/备份位于数据挂载内等情况均拒绝自动恢复。切换与校验过程使用限制在已打开目录内的文件操作，不通过 shell 解压覆盖活动目录。

恢复过程单独写入状态目录的 `data-restore.json`，阶段包括 `preparing`、`staged`、`restoring-database`、`switching`、`installed` 与 `completed`。任一未完成或无法读取的记录都会阻止检查更新、再次升级和再次回退；更新器重启会进入 `manual_intervention` 并尝试停止写入服务。仅修改展示用 `state.json` 不能解除保护。数据目录内保留的 `previous/` 可能含有新版写入及旧密钥，须按敏感业务数据保护，不自动清理；后续 tar 备份排除 `.host-updater-recovery-*` 保留目录，避免递归膨胀。

中断后不自动续跑，也不把文件切换和数据库恢复宣称为跨系统原子事务。人工处理时先保持写入服务停止，核对日志、备份校验值、记录中的挂载路径与恢复目录，按记录阶段检查数据库、活动文件、`snapshot/` 和 `previous/`。只有确认数据库、文件及密钥已匹配，并完成旧版本健康验证后，才归档恢复记录并解除阻塞；不能仅删除 `data-restore.json` 后重试。失败阶段的暂存内容和原文件保留供检查，不对其执行通用缓存清理。

专项回归入口是 `cd backend && go test -count=1 ./internal/hostupdate`，覆盖退出前最终写入、下载与摘要失败、停服失败、备份失败、旧配置保存失败、原容器恢复失败、未就绪响应，回退各前置步骤失败后不再改库或启动服务、素材与密钥恢复、异常归档拒绝、实际子进程退出后的恢复锁，以及新增文件保留副本。命令执行器与健康响应使用隔离替身；它不替代真实 Docker、PostgreSQL 与目标镜像演练。

## 安装与升级约束

自定义源码部署不能直接套用默认更新器。它默认读取 `ddcat-ai/open-ai-canvas` 的 Release，按仓库 owner 选择固定名称的 GHCR 镜像，并用目标 Release 的整份 Compose 替换当前文件；不会合并本地源码修改、额外 Compose overlay、CDN 规则或自定义挂载。多份 Compose、分离的环境文件和分别发布的前后端版本，需要先建立并演练对应的自定义发布合同。

启用前应确认 Release、三个镜像与部署 Compose 都来自同一套已验收的二改发布源，保留实际 project、数据卷、密钥及外部反向代理约定。本地镜像标签、现有服务健康或把 `CANVAS_UPDATER_REPOSITORY` 改成 fork 名称，都不等于这些条件已经满足。默认安装脚本还要求现有 backend/web 为 GHCR digest；源码部署继续使用其已有、已验收的发布与回退流程，直到该适配完成。

GHCR 镜像部署必须把 `CANVAS_IMAGE_TAG` 固定到具体 Release，并把 `CANVAS_BACKEND_IMAGE`、`CANVAS_WEB_IMAGE` 固定到对应 GHCR digest，不可使用 `latest` 或仅使用可变 tag。首次安装时显式指定 Release：

```bash
curl -fsSL https://raw.githubusercontent.com/ddcat-ai/open-ai-canvas/main/scripts/install-server-image.sh \
  | sudo env CANVAS_IMAGE_TAG=v1.5.7.1 bash
```

已有部署只安装更新器时，先确认 `.env` 已包含两个 `@sha256:...` 镜像引用，再执行：

```bash
cd /opt/open-ai-canvas
curl -fsSL https://raw.githubusercontent.com/ddcat-ai/open-ai-canvas/main/scripts/install-host-updater.sh | sudo bash
```

脚本会下载与当前 Release 匹配的 Linux amd64/arm64 二进制和 `SHA256SUMS`，生成随机 `CANVAS_UPDATER_TOKEN`，创建 systemd 服务、Socket 目录、状态目录和 `backups/`。Token 只保存在服务器 `.env` 与 root-only 更新器环境文件中。

## 镜像发布与质量门禁

`main` 推送、`v*` 标签和手动发布统一由 `.github/workflows/publish-images.yml` 编排。发布先调用可复用的 `quality.yml`；PR 仍直接运行质量检查。Go 测试、前端格式、类型、Lint、单测和 Chrome E2E 任一失败，都不能进入镜像构建和发布阶段。若仓库规则配置了必需检查，切换后应核对实际 check 名称，避免仍等待旧的独立 push 工作流。

构建和发布分为以下阶段：

1. 校验 `VERSION`；版本标签必须与文件一致，且存在对应 `CHANGELOG.md` 标题。构建时间取提交时间，同一 SHA 不因重跑而改变。
2. 后端分别在 `ubuntu-24.04`（AMD64）和 `ubuntu-24.04-arm`（ARM64）原生编译，保留 CGO 与三个服务/迁移二进制。支付插件在每个平台的镜像阶段重新打包并执行 smoke；PR 则独立执行双架构 smoke，不依赖发布。
3. 前端 Bun 构建阶段固定到 `BUILDPLATFORM`，静态资源只生成一次，再放入 AMD64/ARM64 nginx 镜像。Bun 与 `web/package.json`、质量检查保持 `1.3.9` 一致。
4. 先推送 `sha-<完整提交>-amd64/arm64` 后端镜像及 `sha-<完整提交>-multi` 前端镜像，以摘要 artifact 传递结果。两种后端架构和前端全部成功后，才从摘要合并发布 manifest，不用可变标签作为合并源。
5. 同一 SHA 的 main/tag 发布串行运行；后到的一轮仍经过质量门禁，然后复用已有 SHA 镜像，不重复编译。只有明确的镜像不存在可以转入构建，鉴权、限流、网络和异常摘要必须报错。
6. 发布保留完整 SHA 和短 SHA 标签；只有版本 tag 推送写入具体版本标签。`main` 只有在仍是远端最新提交时才更新 `latest`，旧提交的慢任务不能覆盖新版本。正式部署由安装器和更新器解析并落盘 digest，不依赖 `latest`。

Go 检查显式使用 `backend/go.sum` 作为缓存依赖键，并上传 `go-test-timings`（JSONL），可按 `Test` / `Elapsed` 定位慢测试。Docker 的后端模块下载保留在普通镜像层，编译步骤可以直接读取；支付插件只按实际 import 下载依赖，不重复预取完整后端模块图。版本参数下移到编译入口。GHA 构建缓存按镜像和架构隔离，避免并行任务共用同一 scope。`go-build` cache mount 只用于同一个 builder 内的复用，当前没有额外的跨 Runner mount 导出方案；不能把它当作持久编译缓存。冷缓存首轮和缓存上传仍可能较慢，需要比较连续两轮的实际耗时。

这套发布流程依赖仓库可使用 GitHub 原生 ARM64 Runner、GHCR 写权限以及构建/下载 artifact 能力。首次上线应核对实际 Runner 排队情况、双架构 manifest、main/tag 同 SHA 复用和质量失败阻断；本地测试不能代替这些云端验收。工作流变更不迁移业务数据库，也不修改服务器 Compose 或数据卷。需要回退 CI 时只回退工作流和 Dockerfile 改动；已发布镜像不会自动撤回，线上版本回退仍按本文的备份与迁移约束执行。

## 运维检查

```bash
sudo systemctl status open-ai-canvas-updater
sudo journalctl -u open-ai-canvas-updater -n 200 --no-pager
sudo ls -lh /opt/open-ai-canvas/backups
sudo sha256sum /opt/open-ai-canvas/backups/*.zip
```

备份文件包含业务数据，应限制为 root 访问并纳入异机备份策略。数据卷本身不是备份。
