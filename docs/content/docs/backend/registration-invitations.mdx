# 用户注册邀请

管理员在「用户管理 → 邀请用户」创建邀请，原「添加用户」继续保留。邀请仅创建普通用户，不支持邀请关系奖励、组织席位或管理员角色。生成链接使用当前浏览器同源地址和 `/i/:code`，不固定生产域名。

## 邀请与注册

短码为 6 位大小写字母和数字，使用系统安全随机源生成，摘要唯一索引与最多 8 次碰撞重试。短码区分大小写。邀请默认 7 天，可设 1–90 天；每条仅允许一个新账号成功注册，管理员可撤销未使用且未过期的邀请。打开邀请、验证、发送验证码和提交失败均不消费邀请。

有效邀请允许在公开注册关闭时注册，但仍必须通过当前启用的邮箱、短信或双重验证，并明确接受服务协议。普通注册和第三方认证沿用原规则；邀请页不展示第三方登录。已登录用户看到「你已登录，无需注册」，可进入工作台或自行切换账号，后端也拒绝已有登录态直接提交邀请注册。

管理员备注仅在管理端展示。公开验证只返回状态，有效时附积分与注册配置，不返回邀请者、内部备注、受邀账号、可用短码或短码存储信息。`valid / expired / revoked / used / invalid` 是邀请状态；网络和服务错误使用失败响应，不能解释为邀请码失效。

## 积分合同

选项固定为 50／100／200／自定义。默认读取当前全局注册赠送值，匹配预设则选中，否则使用自定义。自定义允许 0，禁止空值、负数和超过 1,000,000 积分；最多 6 位小数，转换为整数 microcredits 后提交。

邀请金额是该账号的最终注册赠送总额，**替代全局注册赠送，不叠加**。金额在创建邀请时固定，后续积分政策变化不影响它。账号创建、验证码消费、邀请消费、注册积分流水、管理员审计和注册登录态在同一事务内完成，任一步失败整体回滚。成功响应才携带服务端确认的 `signupBonusMicrocredits`。

邀请赠送复用积分仓库的 `GrantCreditsOnce`，业务键仍为 `signup:<userID>`；即使赠送 0，也写入一次 0 金额流水。因此后续登录的全局赠送恢复流程无法重复赠送。流水保留邀请 ID、创建管理员和注册场景，消费审计保留邀请 ID 与受邀账号 ID。已注册账号不能通过邀请码补领。

## API

全部路径前缀为 `/api`，业务信封、Cookie 登录与失败语义见 [HTTP API](./http-api)。

| 接口 | 权限与合同 |
| --- | --- |
| `POST /auth/invitation/validate` | 公开，JSON `{ code }`；状态 `valid` 时返回 `bonusMicrocredits` 与 `settings`，否则仅返回 `state`。无副作用。 |
| `GET /admin/registration-invitations?page=1&pageSize=20` | 当前有效管理员；分页返回邀请与受邀用户名。 |
| `POST /admin/registration-invitations` | 当前有效管理员；JSON `{ note, bonusMicrocredits, expiresInDays }`，金额必须是整数且不能为空；返回 `{ invitation }`。 |
| `POST /admin/registration-invitations/:id/revoke` | 当前有效管理员；只能撤销有效未消费邀请，竞争失败返回 409。 |
| `POST /auth/verification` | 原注册验证请求可附 `invitationCode`，原验证方式、归属、发送配额和冷却继续生效。 |
| `POST /auth/email-code` | 旧邮箱验证码入口可附 `invitationCode`，同样检查邀请和公开注册边界。 |
| `POST /auth/register` | 原请求可附 `invitationCode`，服务端根据持久邀请决定固定积分和普通用户角色，不接受客户端设置金额或权限。 |

官网关闭注册时的「内测用户邀请」入口复用同一验证 API，成功后跳到 `/i/:code`；已有完整链接直接展示受邀注册表单。不能通过官网入口修改注册开关。

## 限流与存储

6 位空间为 `62^6 = 56,800,235,584`。短码是短期单次注册凭据，必须配合 HTTPS、到期与撤销、数据库条件消费和服务端限流使用，不能作为长期会话令牌。

邀请验证每 IP 每 10 分钟 30 次，提交／验证码每 IP 每 10 分钟各 10 次；每个动作全站每分钟 300 次，每个短码每小时 30 次。管理员每小时最多创建 100 条。原注册和验证码限流继续生效；所有限流键只使用短码摘要。邀请码放在有大小上限的 JSON 中，不放进 API 路径或审计正文；Nginx 访问日志对 `/i/` 路径和相关来源脱敏。

数据库只保存短码摘要和加密短码。加密沿用既有设置密钥，备份与迁移必须保留 `.settings-key`／既有设置加密配置，不能为了更换版本重新生成密钥。新增 `registration_invitations` 表，不回填或修改历史账号、已有积分或运营设置。

## 发布与验收边界

前后端和网关配置应一起发布。迁移只新增邀请表与索引；升级前须做一致性备份，在隔离数据库验证迁移幂等。旧版本若只支持 schema 60，会拒绝 schema 61，不能把「仅新增表」解释为可直接降级应用。发生故障优先保留新数据前向修复；仅在确认升级后无新增业务数据时才可恢复一致的旧应用与数据库备份，不能用旧库覆盖新注册、任务或积分。

后端专项在隔离测试数据库完成注册、验证与并发消费；发送器替代，不投递真实邮件／短信。真实浏览器不代用户勾选协议或执行注册最终提交。上线后可安全检查无效邀请、匿名权限、页面、已有登录态和只读配置；新账号成功注册、实际验证码投递与人工视觉需按 [待测试](../progress/pending-test) 的受限项完成，不以构建或健康检查替代。
